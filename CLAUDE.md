# CLAUDE.md

Manuscript — рабочий стол автора больших нелинейных историй. PWA: работает в браузере и офлайн, ставится на iPhone, iPad, Mac и Windows. Что видит автор — в [README.md](README.md).

Стек: React 19, TypeScript, Vite, TipTap (редактор), Dexie/IndexedDB (хранилище на устройстве), vite-plugin-pwa.

## Команды

```bash
npm run dev        # http://localhost:5173 (превью: "manuscript" в .claude/launch.json)
npm run typecheck
npm test           # vitest, тесты в src/__tests__
npm run build
```

## Где что

- `src/db/` — схема Dexie (`db.ts`), запись и чтение (`repo.ts`), старая синхронизация через Supabase (`cloud.ts`, `sync.ts`).
- `src/lib/` — логика без интерфейса: импорт, экспорт, типографика, маячки, темп, синхронизация с диском (`filesync.ts`, `yandex.ts`).
- `src/views/` — экраны: Текст (`WriteView`), Доска (`BoardView`), Герои, Матчасть, Книга, Настройки.
- `src/components/` — общие части интерфейса.
- `src/styles/app.css` — все стили.

## Данные автора

Тексты живут только на устройствах автора и в облаке автора. В репозиторий, логи и внешние сервисы они не попадают.

- Никогда не удаляй и не переименовывай поля в Dexie.
- Меняй схему только новой версией (`this.version(N)`) с миграцией и тестом на старых данных.
- Удаляй записи флагом `deleted`, не настоящим удалением: на этом держится синхронизация.
- Синхронизацию, импорт и резервную копию меняй только вместе с тестом.

## Синхронизация

Главная синхронизация — свой диск автора: Яндекс Диск (`filesync.ts` + `yandex.ts`). Dropbox и Google Диск добавляются так же, через `FileStore`.

Supabase — старая синхронизация. Не трогай её без просьбы и не строй на ней новое.

## Интерфейс

Пользователи — авторы фанфиков и романов, многие с СДВГ.

- Не добавляй поля, которые автор должен заполнять. Выводи сведения из того, что уже есть.
- Скрывай подробности по умолчанию. Показывай их, когда автор выбрал сцену, ветку или героя.
- Ничто не отвлекает автора во время письма: без всплывающих окон и подсказок поверх текста.
- Делай любое действие на доске отменяемым (Ctrl+Z).
- Держи интерфейс тихим: минимум цвета и рамок.

Решения по доске, веткам и маячкам — в заметках памяти (`planning-decisions`).

## Язык

- Комментарии в коде — на английском.
- Тексты интерфейса и сообщения коммитов — на русском.
- Интерфейс обращается к автору на «ты» и без грамматического рода. Пиши «В прошлый раз», «Написано: 340 слов», не «где остановилась».

## Стили

- Задавай цвета только токенами из `:root`. Не пиши `#hex` прямо в правилах.
- Проверяй правку во всех трёх темах: светлой, тёмной и «бумаге» (`data-theme`).
- Добавляй стили в `app.css` рядом с родственными. Новый файл стилей не заводи.

## Зависимости

- Добавляй npm-пакет только с согласия владелицы.
- Не подключай внешние серверы, CDN и шрифты по ссылке. Приложение работает офлайн и открывается из России без VPN.

## Проверка перед коммитом

1. Запусти `npm run typecheck`.
2. Запусти `npm test`.
3. Проверь правку в превью на ширине компьютера и телефона (375 px).

Если правка касается редактора или ввода текста, напиши в отчёте, что Safari на iPhone не проверен.

Если функция меняет то, что видит автор, обнови раздел README в том же коммите.

## Ветки и публикация

- Работай в ветке `claude/…`.
- Коммить проверенную работу без вопроса.
- Никогда не пушь в `main`. Push в `main` публикует приложение для читателей — это делает владелица.
- Тестовая версия `/preview/` собирается из ветки `claude/writer-app-adhd-tmceif`. Пушь в неё только с разрешения владелицы.

## Распределение работы между моделями

Opus — руководитель и планировщик. Sonnet — исполнитель.

**Opus делает сам:**
- разбирает задачу и уточняет требования;
- проектирует решение и пишет план;
- делит план на шаги и раздаёт их Sonnet;
- проверяет результат: читает дифф, запускает тесты, смотрит превью;
- принимает решения, если шаги конфликтуют или план не сработал.

**Opus отдаёт Sonnet** (через Agent с `model: "sonnet"`):
- написание и правку кода по готовому плану;
- монотонные задачи: массовые замены, переименования, однотипные правки в многих файлах;
- написание тестов по описанным случаям;
- поиск по коду и сбор сведений.

Каждое задание для Sonnet должно быть самодостаточным. Укажи файлы, цель, ограничения и критерий готовности. Sonnet не видит этот разговор.

Мелкую правку в одну-две строки Opus делает сам. Передача такой правки стоит дороже самой правки.
